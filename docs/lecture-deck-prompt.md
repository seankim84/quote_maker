# 수강생 강의자료(슬라이드) 생성 프롬프트

아래 `---` 사이의 내용을 그대로 복사해 Claude 에게 붙여넣으세요.

---

당신은 비개발자를 가르치는 기술 교육자이자 프레젠테이션 디자이너입니다.

저는 "Claude Code 로 실무 도구 만들기" 수업의 강사입니다.
수강생은 **코딩을 배운 적 없는 직장인**입니다. 엑셀은 쓸 수 있지만 프로그래밍 용어는 모릅니다.

제가 Claude Code 와 함께 완성한 프로젝트를 수강생에게 설명할 **슬라이드 덱**을 만들어 주세요.

## 작성 규칙 (가장 중요)

1. **전문용어를 쓰면 반드시 그 자리에서 쉬운 말로 풀어주세요.**
   나쁜 예: "pandas 로 DataFrame 을 처리합니다"
   좋은 예: "pandas — **파이썬용 엑셀**입니다. 표 데이터를 다룹니다"
2. **모든 툴과 모듈에 '비유'를 하나씩 붙이세요.** 비유 없이 지나가지 마세요.
3. 한 슬라이드 = 한 가지 메시지. 슬라이드 제목만 읽어도 흐름이 보이게.
4. 한 슬라이드에 글머리 5개 이하, 한 줄 25자 이내.
5. 모든 텍스트는 한국어. 툴 이름(Streamlit 등)만 영문 그대로.
6. 코드는 꼭 필요할 때만, 3~5줄까지. 코드를 보여줄 땐 **무엇을 하는 줄인지** 한국어로 옆에 적어주세요.
7. "쉽습니다", "간단합니다" 같은 말은 쓰지 마세요. 수강생이 어려워하면 거짓말이 됩니다.

## 슬라이드 구성 (4부, 총 30~35장)

### 1부. 무엇을 만들었나 (4장)
- 문제 상황: 베트남 B2B 사무용품 유통사. 고객이 카톡·메일로 "모니터 20대, 키보드 30개 견적 주세요" 라고 보내면, 담당자가 엑셀에서 상품 찾고 단가 옮겨 적고 재고 확인하고 계산해서 양식에 붙이는 데 20~30분
- 만든 것: 고객 문장을 **붙여넣기 한 번**으로 견적서 PDF 까지
- 완성 화면 5개: Dashboard / New Quotation / Product Search / Quotation Preview / Settings
- 데이터 흐름 한 장 (아래 "흐름도" 자료 사용)

### 2부. 어떤 순서로 만들었나 (12장)
10단계를 순서대로. 단계마다 **4줄 고정**:
- 무엇을 만들었나
- 왜 이 순서였나
- 어떻게 확인했나

그리고 2부 끝에 **"왜 한 번에 다 만들지 않았나"** 슬라이드를 넣어주세요. 핵심 메시지:
> 한 번에 다 만들면 에러가 나도 **설정 문제인지 코드 문제인지 구분이 안 됩니다.**
> 각 단계는 다음 단계를 검증하는 수단입니다.

### 3부. 어떤 툴을 썼나 (10장)
아래 "툴 자료"와 "모듈 자료"를 그대로 활용하세요. 설치법은 쓰지 마세요. **그 툴이 왜 그 자리에 있는지**만.

### 4부. 실제로 터진 문제들 (8장) ← 이 수업의 핵심
아래 "실제 문제 자료" 7개를 각각 한 장씩. 마지막 장은 교훈 정리.

# 자료 (아래 사실만 사용하세요. 내용을 추측하거나 추가하지 마세요)

## 흐름도

```
고객 문의 (자연어)
   ↓  Claude API 가 해석
상품명 + 수량 + 요청 납기
   ↓  Google Sheets 에서 조회
실제 상품 · 단가 · 재고
   ↓  파이썬이 계산
할인 → 세금 → 최종 금액
   ↓  사람이 검토·수정
   ↓
PDF 견적서 + 이메일 초안(한/영/베)
```

## 10단계 개발 순서

| 단계 | 만든 것 | 왜 이 순서 | 어떻게 확인 |
|---|---|---|---|
| 1 | 폴더 구조, 설정 읽기, 빈 화면 5개 | 키 없이도 화면이 뜨는지 먼저 확인해야, 나중에 에러 났을 때 설정 문제인지 코드 문제인지 구분됨 | `streamlit run` 으로 화면 뜸, 테스트 3개 |
| 2 | 가상 상품 34종·거래처 8곳 CSV, 시트 양식 | 읽을 데이터가 없으면 3단계 연결이 됐는지 알 수 없음 | 데이터 검증 테스트 9개 |
| 3 | Google Sheets 읽기 전용 연결 | AI 가 뽑은 상품명을 시트와 대조해야 하므로 읽기를 먼저 못 박음 | 실제 시트에서 34종 읽음, 틀린 시트 ID 로 에러 안내 확인 |
| 4 | 고객 문의 → JSON 구조화 (Claude + Mock) | 여기서부터 AI. 앞 단계가 안정돼야 AI 결과가 틀렸는지 판단 가능 | 실제 Claude 호출 3회, 테스트 22개 |
| 5 | 상품 매칭 · 재고 확인 | AI 가 만든 검색어로 실제 상품을 찾는 단계 | 2단계에 심어둔 함정 5개가 모두 걸림 |
| 6 | 금액 계산 | 상품이 확정돼야 계산할 것이 생김 | 손으로 계산한 값을 테스트에 적어 비교 |
| 7 | 검토·수정 화면 | 계산이 맞아야 수정 후 재계산을 확인할 수 있음 | 할인율 10%→15% 바꿔 금액 변화 확인 |
| 8 | PDF 견적서 + 이메일 초안 3개 언어 | 최종 산출물. 앞의 모든 값이 모여야 만들 수 있음 | 실제 PDF 생성, 3개 언어 실제 Claude 호출 |
| 9 | 오류 처리 점검 · 전체 테스트 | 기능이 다 모인 뒤에야 "같이 쓸 때" 문제가 보임 | 설계 결함 4개 발견·수정 |
| 10 | 배포 준비 | 내 컴퓨터에서만 되는 것과 남이 쓰는 것은 다름 | 깨끗한 복사본으로 테스트 164개 통과 |

**2단계의 "함정 데이터"를 꼭 강조해 주세요.** 일부러 심어둔 것들:
- 무선마우스 재고 18개 → 30개 주문하면 12개 부족 (재고 경고 확인용)
- 화이트보드 마커 재고 0 (품절 표시 확인용)
- 모니터 3종 (유사 상품 선택 요청 확인용)
- 단종 상품 1개 (검색 제외 확인용)
- 한글 이름·베트남어 이름 (PDF 폰트 확인용)

→ 교훈: **테스트할 데이터를 먼저 설계해야, 기능이 진짜 동작하는지 확인할 수 있습니다.**

## 모듈 자료 — 우리가 만든 파일들 (식당 비유로 설명하세요)

**큰 그림: 이 프로젝트는 식당처럼 만들어졌습니다.**
- `app.py` = **홀** (손님이 보는 곳)
- `core/` = **주방** (실제 조리)
- 홀 인테리어를 바꿔도 주방은 그대로 → 나중에 화면을 다른 기술로 바꿔도 핵심 로직은 재사용

| 파일 | 식당에서 치면 | 하는 일 |
|---|---|---|
| `app.py` | 홀 · 메뉴판 · 주문서 | 화면만 담당. 계산·AI 호출 없음 |
| `core/config.py` | 금고 열쇠 보관함 | API 키·설정 읽기. 화면에 키를 보여주지 않음 |
| `core/sheets.py` | 창고 담당자 | 구글시트에서 상품·거래처 읽어옴 |
| `core/extract.py` | 통역사 | 고객 문장 → 상품명·수량으로 번역 |
| `core/matching.py` | 창고에서 물건 찾는 직원 | 검색어로 실제 상품 찾기, 재고 비교 |
| `core/pricing.py` | 계산원 | 할인 → 세금 → 최종 금액 |
| `core/pdf.py` | 인쇄소 | 견적서 PDF 제작 |
| `core/email_draft.py` | 비서 | 고객에게 보낼 메일 초안 작성 |
| `core/quota.py` | 수도 계량기 | 공개 앱에서 AI 호출 횟수 제한 |
| `tests/` | 위생 검사원 | 164가지 자동 점검 |

**강조할 설계 원칙 3개:**
1. **AI 는 글만, 계산은 코드가** — 금액을 AI 에게 맡기면 매번 다른 답이 나올 수 있습니다
2. **AI 가 상품과 가격을 만들어낼 수 없게** — 상품은 구글시트에만 존재합니다
3. **확실하지 않으면 사람에게 묻는다** — 비슷한 상품이 여러 개면 자동 선택하지 않습니다

## 실제 문제 자료 (7장, 각 한 슬라이드)

각 장을 **"증상 → 원인 → 교훈"** 3단으로 구성하세요.

**1. 파이썬의 `round(2.5)` 는 3 이 아니라 2 입니다**
- 증상: 반올림 결과가 예상과 다름
- 원인: 파이썬 기본 반올림은 "은행원 반올림" 이라 2.5 를 2 로 내립니다
- 교훈: 돈 계산은 기본 기능을 믿지 말고 확인하세요. 테스트에 `assert round(2.5) == 2` 를 넣어 "기본 함수를 썼다면 틀렸을 것"을 증거로 남겼습니다

**2. "A4 용지" 의 4 를 주문 수량으로 읽었습니다**
- 증상: `A4 용지 1,200장` → 수량 4개로 인식
- 원인: 글에서 숫자를 찾는 규칙이 상품명 안의 숫자까지 집어냄
- 교훈: 테스트를 먼저 써두면 이런 버그를 사람이 발견하기 전에 잡습니다

**3. 이 컴퓨터의 글꼴 332개 중 한글·베트남어가 모두 되는 것은 1개뿐이었습니다**
- 증상: 베트남어 성조 글자가 PDF 에서 깨질 위험
- 원인: PDF 도구는 글자별로 글꼴을 바꿔주지 않음. 한 글꼴에 모든 글자가 있어야 함
- 교훈: "될 거야" 로 넘기지 말고 **직접 확인**하세요. 글꼴 전체를 검사하는 코드를 만들어 확인했습니다

**4. 시트에 없는 품목 1개가 견적 전체를 막았습니다**
- 증상: 문의에 "지게차" 가 섞이면 견적을 아예 만들 수 없음
- 원인: "미확정 항목이 있으면 중단" 규칙이 너무 엄격했음. 견적서에는 "확인 필요" 를 표시하는 기능이 이미 있었는데 **도달할 수 없는 코드**였음
- 교훈: 전체를 한 번 돌려보는 점검(9단계)이 없으면 이런 모순을 못 찾습니다

**5. 화면을 옮겼다 돌아오면 입력이 전부 사라졌습니다**
- 증상: 견적서 미리보기를 본 뒤 돌아오면 거래처·할인율·수정한 수량이 초기화
- 원인: Streamlit 은 화면에 보이지 않는 입력칸의 값을 버립니다
- 교훈: 프레임워크의 숨은 동작은 문서보다 **직접 돌려봐야** 드러납니다

**6. 이전 고객에게 보낼 이메일 초안이 화면에 남아 있었습니다**
- 증상: 두 번째 견적을 만들어도 첫 번째 고객 이름이 적힌 초안이 그대로 표시
- 원인: 새 견적을 시작할 때 이전 결과를 지우지 않음
- 교훈: **조용한 사고가 가장 위험합니다.** 에러는 눈에 보이지만, 틀린 내용이 조용히 남는 건 보이지 않습니다

**7. `.env` 파일은 왜 서버에서 읽히지 않나**
- 증상: 로컬에서는 되는데 배포하면 "설정이 없다" 는 에러
- 원인: `.env` 는 보안을 위해 GitHub 에 올리지 않습니다. 서버는 GitHub 에서 코드를 받아오므로 그 파일이 없습니다
- 교훈: 비밀값은 **환경마다 따로** 넣습니다. 내 컴퓨터는 `.env`, 서버는 Secrets 입력란

**마지막 장 — 교훈 정리:**
> AI 와 함께 개발하면 코드는 빨리 나옵니다.
> 빨라진 만큼 **확인하는 방법**을 함께 만들어야 합니다.
> 이 프로젝트에서 테스트 164개가 그 역할을 했습니다.
